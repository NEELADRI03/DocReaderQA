# S0.4.2 — Login, register and the main layout

> **As a User, I want login and register screens and the main layout, so that I can enter the app.**

**Acceptance criteria:**
1. **Login and register pages with validation.**
2. **After login, a three-pane layout** (library, chat, viewer) **with empty states.**
3. **Logout clears the token.**

**Size:** M (1–2 days). Depends on S0.4.1 (router, API client, `meQuery`), which must be merged first.

**Out of scope, don't build it yet:**
- **Anything inside the panes.** Collections and the collection picker are S1.1.1, upload is S1.2.x, chat is Phase 2, and the PDF viewer is S2.x. This story only builds the frame and its empty states.
- **Password reset, "remember me", email verification.** Not in v1.
- **Server-side logout or token revocation.** The tokens are stateless JWTs (S0.3.2), so logout means the browser forgets them.
- **Resizable panes, and a mobile layout beyond stacking.** Below 1024 px wide, the panes stack. Nothing more.

## Architecture

```
            no tokens                               tokens
                │                                      │
 ┌──────────────▼──────────────┐       ┌───────────────▼────────────────────────────────┐
 │ GuestOnly                   │       │ RequireAuth (S0.4.1): GET /auth/me once        │
 │  /login     LoginPage       │       │  AppLayout: header ─ DocQA ··· ann@… [Log out] │
 │  /register  RegisterPage    │       │   / WorkspacePage                              │
 │                             │       │   ┌──────────┬───────────────┬───────────────┐ │
 │  tokens? → Navigate to "/"  │       │   │ Library  │ Chat          │ Viewer        │ │
 └──────────────┬──────────────┘       │   │ empty    │ empty, input  │ empty         │ │
                │                      │   │ state    │ disabled      │ state         │ │
     submit: validate in the browser   │   └──────────┴───────────────┴───────────────┘ │
     (validation.ts), then call the    └───────────────┬────────────────────────────────┘
     API through useMutation                           │ Log out: clear the tokens and the
     ok → save tokens → navigate("/")                  │ query cache → /login
     error → message under its field                   ▼
             or above the form                      /login
```

**Two layers of validation.** The browser checks what it can before sending: an empty field, a malformed email, a password shorter than 8 characters, a confirmation that doesn't match. The backend stays the authority: its 422 `details`, `EMAIL_TAKEN` and `INVALID_CREDENTIALS` are shown in the same places as the browser's own messages.

## Step 2 — `src/lib/validation.ts`: the form rules

```ts
// Same limits as RegisterRequest in docqa-backend/app/schemas/auth.py
export const PASSWORD_MIN_LENGTH = 8
export const PASSWORD_MAX_LENGTH = 128

// Deliberately loose: something@something.something. The backend's EmailStr has the final say.
const EMAIL_PATTERN = /^[^\s@]+@[^\s@]+\.[^\s@]+$/

// One message per field, keyed by the input's name
export type FieldErrors = Partial<Record<string, string>>

export interface LoginValues {
  email: string
  password: string
}

export interface RegisterValues extends LoginValues {
  confirmPassword: string
}

function emailError(email: string): string | undefined {
  if (email === '') return 'Enter your email address.'
  if (!EMAIL_PATTERN.test(email)) return 'Enter an email address like name@example.com.'
  return undefined
}

export function validateLogin({ email, password }: LoginValues): FieldErrors {
  return withoutEmpty({
    email: emailError(email),
    // No length rules here: they're for choosing a password, and the backend rejects a wrong one
    password: password === '' ? 'Enter your password.' : undefined,
  })
}

export function validateRegister({
  email,
  password,
  confirmPassword,
}: RegisterValues): FieldErrors {
  let passwordError: string | undefined
  if (password.length < PASSWORD_MIN_LENGTH) {
    passwordError = `Use at least ${PASSWORD_MIN_LENGTH} characters.`
  } else if (password.length > PASSWORD_MAX_LENGTH) {
    passwordError = `Use at most ${PASSWORD_MAX_LENGTH} characters.`
  }
  return withoutEmpty({
    email: emailError(email),
    password: passwordError,
    confirmPassword: confirmPassword === password ? undefined : 'The passwords don’t match.',
  })
}

export function hasErrors(errors: FieldErrors): boolean {
  return Object.keys(errors).length > 0
}

function withoutEmpty(errors: FieldErrors): FieldErrors {
  return Object.fromEntries(Object.entries(errors).filter(([, message]) => message !== undefined))
}
```

### How the code works

- **Plain functions, no React.** They take values and return `{ fieldName: message }`. An empty object means valid. That makes them easy to test (Step 6), and the pages only need to call one function.
- **The limits copy the backend's** `PASSWORD_MIN_LENGTH` and `PASSWORD_MAX_LENGTH` (S0.3.1). If you ever change them there, change them here too. If the two drift apart, nothing breaks: the backend's 422 appears under the password field instead.
- **The email check is deliberately loose.** Real email syntax is complicated, and a strict regex rejects valid addresses. This one catches typos such as a missing `@` or domain. The backend's `EmailStr` decides the rest, and its message appears under the field (tested in Step 6).
- **The login form doesn't check password length.** S0.3.2 made the same choice on the backend: length rules are for choosing a password, and a user with an older, shorter password must still be able to log in.

## Step 3 — `src/lib/useFormErrors.ts`: showing the errors

```ts
import { useRef, useState, type FormEvent } from 'react'

import { ApiError } from './api'
import type { FieldErrors } from './validation'

// Field errors and a form-level error for one form, shared by the login and register screens
export function useFormErrors() {
  const formRef = useRef<HTMLFormElement>(null)
  const [fieldErrors, setFieldErrors] = useState<FieldErrors>({})
  const [formError, setFormError] = useState<string | null>(null)

  function showErrors(fields: FieldErrors, form: string | null = null) {
    setFieldErrors(fields)
    setFormError(form)
    // Move focus to the first field with a problem, in the order the fields appear
    const elements = Array.from(formRef.current?.elements ?? []) as HTMLInputElement[]
    elements.find((element) => fields[element.name])?.focus()
  }

  // Turns a failed API call into messages. fieldForCode puts a code's message under a field,
  // such as EMAIL_TAKEN under the email input.
  function showServerError(error: Error, fieldForCode: Record<string, string> = {}) {
    if (!(error instanceof ApiError)) {
      showErrors({}, 'Something went wrong. Please try again.')
    } else if (error.code === 'VALIDATION_ERROR' && error.details.length > 0) {
      showErrors(Object.fromEntries(error.details.map((d) => [d.field, d.message])))
    } else if (fieldForCode[error.code]) {
      showErrors({ [fieldForCode[error.code]]: error.message })
    } else {
      showErrors({}, error.message)
    }
  }

  // onChange on the <form>: typing in a field hides that field's error
  function clearFieldError(event: FormEvent<HTMLFormElement>) {
    const { name } = event.target as HTMLInputElement
    if (fieldErrors[name]) setFieldErrors((errors) => ({ ...errors, [name]: undefined }))
  }

  return { formRef, fieldErrors, formError, showErrors, showServerError, clearFieldError }
}
```

### How the code works

Every error ends up in one of two places:

| Error | Where it shows |
|---|---|
| The browser's own checks (Step 2) | Under its field |
| 422 `VALIDATION_ERROR` with `details` | Under each named field. The backend's `field` names (`email`, `password`) match the inputs' `name`s. |
| A code in `fieldForCode` (`EMAIL_TAKEN`) | Under that field |
| Anything else: `INVALID_CREDENTIALS`, `NETWORK_ERROR`, a 500 | Above the form |

- **Focus moves to the first field with a problem.** Keyboard and screen-reader users land right where the fix is needed. The order comes from the form itself (`form.elements`), not from the order of the keys in the object.
- **Typing clears that field's error, and only that one.** One `onChange` on the `<form>` catches input from every field, because change events bubble up.
- **The error type is plain `Error`,** because that's what TanStack Query's `useMutation` passes to `onError`. `instanceof ApiError` narrows it.

## Step 4 — The form components

### `src/components/TextField.tsx`

```tsx
import { useId, type InputHTMLAttributes } from 'react'

interface TextFieldProps extends InputHTMLAttributes<HTMLInputElement> {
  label: string
  name: string
  error?: string
  hint?: string
}

// A labelled input whose hint or error is read out by screen readers with the field
export default function TextField({ label, name, error, hint, ...inputProps }: TextFieldProps) {
  const id = useId()
  const describedBy = error ? `${id}-error` : hint ? `${id}-hint` : undefined

  return (
    <div>
      <label htmlFor={id} className="block text-sm font-medium text-slate-700 dark:text-slate-200">
        {label}
      </label>
      <input
        id={id}
        name={name}
        aria-invalid={error ? true : undefined}
        aria-describedby={describedBy}
        className="mt-1 block w-full rounded-md border border-slate-300 bg-white px-3 py-2 text-slate-900 shadow-sm focus:border-indigo-500 focus:outline-none focus:ring-2 focus:ring-indigo-500/30 aria-invalid:border-red-500 dark:border-slate-600 dark:bg-slate-800 dark:text-slate-100"
        {...inputProps}
      />
      {error ? (
        <p id={`${id}-error`} className="mt-1 text-sm text-red-600 dark:text-red-400">
          {error}
        </p>
      ) : (
        hint && (
          <p id={`${id}-hint`} className="mt-1 text-sm text-slate-500 dark:text-slate-400">
            {hint}
          </p>
        )
      )}
    </div>
  )
}
```

- **`useId()`** gives each field a unique, stable ID, so `<label htmlFor>` and `aria-describedby` point at the right elements even with two forms on a page.
- **`aria-invalid`** tells screen readers the field has a problem. The `aria-invalid:border-red-500` class turns the border red from the same attribute, so the look and the accessibility can't drift apart.
- **`aria-describedby`** makes a screen reader read the error (or the hint) together with the label: *"Password, invalid, Use at least 8 characters."* The tests check this with `toHaveAccessibleDescription`.
- **The error replaces the hint** rather than appearing under it, so there's only ever one line of help text.

### `src/components/SubmitButton.tsx`

```tsx
interface SubmitButtonProps {
  pending: boolean
  children: string
  pendingText: string
}

export default function SubmitButton({ pending, children, pendingText }: SubmitButtonProps) {
  return (
    <button
      type="submit"
      // aria-disabled, not disabled: the button stays focusable, and a double click can't resubmit
      aria-disabled={pending}
      className="w-full rounded-md bg-indigo-600 px-4 py-2 font-medium text-white hover:bg-indigo-500 focus:outline-none focus-visible:ring-2 focus-visible:ring-indigo-500 focus-visible:ring-offset-2 aria-disabled:cursor-wait aria-disabled:opacity-70"
    >
      {pending ? pendingText : children}
    </button>
  )
}
```

`disabled` would remove the focused button from the tab order in the middle of submitting, and keyboard focus would jump to the top of the page. `aria-disabled` keeps it focusable. The pages ignore a second submit while one is pending (`if (mutation.isPending) return`).

## Step 5 — The pages

### `src/routes/LoginPage.tsx` (replace)

```tsx
import { useMutation } from '@tanstack/react-query'
import type { FormEvent } from 'react'
import { Link, useLocation, useNavigate, type Location } from 'react-router'

import AuthCard from '../components/AuthCard'
import FormAlert from '../components/FormAlert'
import SubmitButton from '../components/SubmitButton'
import TextField from '../components/TextField'
import { login } from '../lib/auth'
import { useFormErrors } from '../lib/useFormErrors'
import { hasErrors, validateLogin, type LoginValues } from '../lib/validation'

export default function LoginPage() {
  const navigate = useNavigate()
  const location = useLocation()
  const { formRef, fieldErrors, formError, showErrors, showServerError, clearFieldError } =
    useFormErrors()

  const loginMutation = useMutation({
    mutationFn: ({ email, password }: LoginValues) => login(email, password),
    onSuccess: () => {
      // Back to the page RequireAuth or the API client sent us here from
      const from = (location.state as { from?: Location } | null)?.from
      navigate(from ?? '/', { replace: true })
    },
    // INVALID_CREDENTIALS shows above the form: the backend doesn't say which field was wrong
    onError: (error) => showServerError(error),
  })

  function onSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault()
    if (loginMutation.isPending) return

    const form = new FormData(event.currentTarget)
    const values: LoginValues = {
      email: String(form.get('email')).trim(),
      password: String(form.get('password')),
    }
    const errors = validateLogin(values)
    showErrors(errors)
    if (!hasErrors(errors)) loginMutation.mutate(values)
  }

  return (
    <AuthCard
      title="Log in"
      footer={
        <>
          New to DocQA?{' '}
          <Link to="/register" className="font-medium text-indigo-600 hover:underline">
            Create an account
          </Link>
        </>
      }
    >
      {/* noValidate: our messages replace the browser's bubbles, so every check looks the same */}
      <form
        ref={formRef}
        noValidate
        onSubmit={onSubmit}
        onChange={clearFieldError}
        className="space-y-4"
      >
        <FormAlert message={formError} />
        <TextField
          label="Email"
          name="email"
          type="email"
          autoComplete="email"
          error={fieldErrors.email}
        />
        <TextField
          label="Password"
          name="password"
          type="password"
          autoComplete="current-password"
          error={fieldErrors.password}
        />
        <SubmitButton pending={loginMutation.isPending} pendingText="Logging in…">
          Log in
        </SubmitButton>
      </form>
    </AuthCard>
  )
}
```

### `src/routes/RegisterPage.tsx` (new)

```tsx
import { useMutation } from '@tanstack/react-query'
import type { FormEvent } from 'react'
import { Link, useNavigate } from 'react-router'

import AuthCard from '../components/AuthCard'
import FormAlert from '../components/FormAlert'
import SubmitButton from '../components/SubmitButton'
import TextField from '../components/TextField'
import { login, register } from '../lib/auth'
import { useFormErrors } from '../lib/useFormErrors'
import {
  hasErrors,
  PASSWORD_MIN_LENGTH,
  validateRegister,
  type RegisterValues,
} from '../lib/validation'

export default function RegisterPage() {
  const navigate = useNavigate()
  const { formRef, fieldErrors, formError, showErrors, showServerError, clearFieldError } =
    useFormErrors()

  const registerMutation = useMutation({
    // Register returns the user but no tokens, so log straight in with the same details
    mutationFn: async ({ email, password }: RegisterValues) => {
      await register(email, password)
      await login(email, password)
    },
    onSuccess: () => navigate('/', { replace: true }),
    onError: (error) => showServerError(error, { EMAIL_TAKEN: 'email' }),
  })

  function onSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault()
    if (registerMutation.isPending) return

    const form = new FormData(event.currentTarget)
    const values: RegisterValues = {
      email: String(form.get('email')).trim(),
      password: String(form.get('password')),
      confirmPassword: String(form.get('confirmPassword')),
    }
    const errors = validateRegister(values)
    showErrors(errors)
    if (!hasErrors(errors)) registerMutation.mutate(values)
  }

  return (
    <AuthCard
      title="Create your account"
      footer={
        <>
          Already have an account?{' '}
          <Link to="/login" className="font-medium text-indigo-600 hover:underline">
            Log in
          </Link>
        </>
      }
    >
      <form
        ref={formRef}
        noValidate
        onSubmit={onSubmit}
        onChange={clearFieldError}
        className="space-y-4"
      >
        <FormAlert message={formError} />
        <TextField
          label="Email"
          name="email"
          type="email"
          autoComplete="email"
          error={fieldErrors.email}
        />
        <TextField
          label="Password"
          name="password"
          type="password"
          // Tells password managers to offer a new, generated password
          autoComplete="new-password"
          hint={`At least ${PASSWORD_MIN_LENGTH} characters.`}
          error={fieldErrors.password}
        />
        <TextField
          label="Confirm password"
          name="confirmPassword"
          type="password"
          autoComplete="new-password"
          error={fieldErrors.confirmPassword}
        />
        <SubmitButton pending={registerMutation.isPending} pendingText="Creating account…">
          Create account
        </SubmitButton>
      </form>
    </AuthCard>
  )
}
```

### How the pages work

- **`useMutation`** is TanStack Query's tool for calls that change something (log in, register), as opposed to `useQuery`, which reads. It tracks `isPending` for the button, and calls `onSuccess` or `onError` when the request finishes.
- **The flow on submit:** read the values with `FormData`, then validate in the browser. If anything's wrong, show it and stop. Otherwise call the API. The inputs aren't React state (they're "uncontrolled"), so the values stay in the fields after a failed attempt and there's nothing to keep in sync.
- **`noValidate`** turns off the browser's own pop-up bubbles for `type="email"`. Every message then comes from one place and looks the same, and the tests can check them.
- **The email is trimmed.** A space pasted along with an address is a common reason a login fails.
- **`INVALID_CREDENTIALS` shows above the form, not under a field.** The backend deliberately doesn't say whether the email or the password was wrong (S0.3.2), so the frontend doesn't guess.
- **Register, then log straight in.** `POST /auth/register` returns the user but no tokens, so the page calls `login` with the same details. One click takes a new user straight into the app. If the API went down between the two calls, the account exists but the user is still on the form. They'll see the network error, and a retry says `EMAIL_TAKEN`. They log in instead. It's rare and harmless.
- **`EMAIL_TAKEN` goes under the email field,** because that's the field the user has to change.
- **The confirmation never leaves the browser.** Only `email` and `password` are sent, which a test checks.
- **`autoComplete`** values let password managers do the right thing: fill in `current-password` on login, offer to generate a `new-password` on register.

### `src/routes/GuestOnly.tsx` (new)

```tsx
import { Navigate, Outlet } from 'react-router'

import { getTokens } from '../lib/tokens'

// Wraps /login and /register: someone already logged in goes straight to the app
export default function GuestOnly() {
  return getTokens() ? <Navigate to="/" replace /> : <Outlet />
}
```

It's the mirror of `RequireAuth`. A logged-in user who opens `/login` from a bookmark lands in the app instead of on a form they don't need. If their tokens turn out to be dead, `RequireAuth`'s `/auth/me` call sends them back to `/login` with the tokens cleared, so this can't loop.

## Step 6 — The layout: header, three panes, logout

### `src/layout/AppLayout.tsx` (new)

```tsx
import { useQuery, useQueryClient } from '@tanstack/react-query'
import { Outlet, useNavigate } from 'react-router'

import { logout, meQuery } from '../lib/auth'

// The frame around every logged-in page: a header with the user and Log out, then the page
export default function AppLayout() {
  // Already in the cache: RequireAuth loaded it before rendering this
  const { data: user } = useQuery(meQuery)
  const queryClient = useQueryClient()
  const navigate = useNavigate()

  function onLogout() {
    logout()
    // Forget everything cached for this user, so the next person to log in can't see it
    queryClient.clear()
    navigate('/login', { replace: true })
  }

  return (
    <div className="flex h-screen flex-col bg-white text-slate-900 dark:bg-slate-900 dark:text-slate-100">
      <header className="flex items-center justify-between border-b border-slate-200 px-4 py-2 dark:border-slate-700">
```

**Logout (acceptance criterion 3) does three things:**
1. `logout()` removes `docqa.tokens` from `localStorage` (S0.4.1's `clearTokens`).
2. `queryClient.clear()` throws away every cached response: the user now, and collections and documents in later stories. Without it, the next person to log in on this browser could briefly see the previous user's data. A test checks the cache is empty.
3. `navigate('/login', { replace: true })` replaces the app's history entry. After logging out, **Back** can't show the app, and if someone tries anyway, `RequireAuth` finds no tokens and redirects.

No API call is made, which is also tested. The tokens are stateless, so there's nothing to tell the server. The refresh token stays technically valid until it expires, but nothing has it any more. A server-side revocation list would be Phase 4 work.

### How the layout works

- **The architecture's three panes:** documents on the left, chat in the centre, and a PDF viewer on the right that opens to a cited page.
- **The grid is `16rem | 1fr | 1fr`.** The library is a fixed 256 px list. Chat and viewer share the rest equally. `minmax(0, 1fr)` instead of `1fr` lets a column shrink below its content's width, so a long line of text can't push the viewer off screen.
- **Each pane scrolls on its own.** The page is exactly the screen's height (`h-screen`), and `min-h-0` together with `overflow-y-auto` makes each pane scroll independently. A long chat won't scroll the library away.
- **Below 1024 px, the panes stack** in one scrollable column. That's enough for now; a mobile design with tabs between panes would be a later story.
- **Empty states say what will appear and how to get there,** not just "Nothing here". The chat box is shown but disabled, which matches the architecture's rule: *"Disable asking until at least one document is ready."* Phase 2 enables it.
- **Each pane is a `<section>` labelled by its heading,** which gives it the ARIA role `region`. Screen-reader users can jump between Library, Chat and Viewer, and the tests find the panes the same way.
- **`AppLayout` and `WorkspacePage` are separate** on purpose. The header stays the same on every logged-in page, and later stories (for example `/collections/:id`) only add routes under `AppLayout`.

### How the tests work

| Acceptance criterion | Tests |
|---|---|
| 1. Login and register with validation | `validation.test.ts` covers the rules. The page tests cover the browser's checks, the server's 401/409/422 shown in the right place, focus, and the error clearing as you type. |
| 2. Three panes with empty states after login | "logs in and opens the app" and "creates the account..." end on the workspace. "shows the three panes..." checks each pane's empty state and the disabled chat box. |
| 3. Logout clears the token | "logs out: ..." checks that the tokens and the cache are gone, the URL is `/login`, and no API call was made. |

- **`userEvent`** types and clicks the way a person does: focus, a key event for each character, then the click. It catches problems that setting values directly would hide, such as an `onChange` that never fires.
- **`toHaveAccessibleDescription`** checks what a screen reader reads with the field. It passes only if `aria-describedby` points at the right message, so it tests the wiring, not just that some red text appeared somewhere.
- **The whole app is rendered for every page test** (`renderApp`), with the real routes, `RequireAuth`, `GuestOnly` and the query cache. The tests check where the user ends up, not just that a function was called.

## Common problems

| Symptom | Cause | Fix |
|---|---|---|
| No styles at all: plain browser defaults | The Tailwind plugin or the CSS import is missing | `tailwindcss()` in `plugins` (Step 1), and `@import 'tailwindcss';` in `src/index.css` |
| `Cannot find package '@tailwindcss/vite'` in the container only | The old anonymous `node_modules` volume | `docker compose up -d --renew-anon-volumes frontend` |
| The browser's own *"Please include an '@'"* bubble appears | `noValidate` missing on the `<form>` | Step 5 |
| Clicking **Log in** twice sends two requests | No `isPending` check in `onSubmit` | `if (loginMutation.isPending) return` (Step 5) |
| A 422 message doesn't appear under its field | The input's `name` differs from the backend's `field` | Keep the names `email` and `password`, exactly as in the request body |
| After logout, the next user briefly sees the previous user's email | `queryClient.clear()` missing | Step 6. The logout test catches this. |
| Test: `Unable to find role "region"` | The `<section>` has no accessible name | `aria-labelledby` pointing at the pane's heading (Step 6) |
| Test: `toHaveAccessibleDescription` fails | `aria-describedby` points at an ID that doesn't exist | Check the `${id}-error` / `${id}-hint` IDs in `TextField` |
| Test: `Unexpected API call: GET /auth/me` | A test that ends in the app has no `/auth/me` handler | Add `'GET /auth/me': () => json(200, USER)` |
| After registering, *"Could not reach the server"*, and a retry says `EMAIL_TAKEN` | The API dropped between register and login | The account exists: log in. See "Register, then log straight in" in Step 5. |
| Panes overflow sideways on a narrow screen | `1fr` instead of `minmax(0,1fr)` | Step 6 |
